# OrderFlow: учебный Go backend

## Цель

Создать сервис заказов с REST API, PostgreSQL, Kafka, Redis и фоновыми обработчиками. Пройти путь от типов и тестов Go до диагностики конкурентных ошибок и восстановления после сбоев.

Исходный уровень: middle PHP / junior Python. Основы программирования не повторяем; изучаем особенности Go и инженерные решения через практику. Проект не гарантирует уровень middle, но даёт проверяемые навыки для Go backend и материал для собеседований.

Проходи модули последовательно. В каждом: изучить темы → реализовать задачи → выполнить проверки → объяснить решения своими словами → отметить чекбоксы. Не подключай Kafka и Redis до соответствующих модулей. Код пишешь самостоятельно; этот файл задаёт требования, а не готовое решение.

## Продукт и границы

Пользователь читает каталог, создаёт заказ и получает результат асинхронного резервирования товаров. При достаточных остатках заказ подтверждается, иначе отклоняется. Результат создаёт уведомление; позднее оно отправляется в тестовый webhook.

Основной поток:

```text
HTTP → заказ + outbox в PostgreSQL → publisher → Kafka
Kafka → order-worker → резервирование + статус + outbox в PostgreSQL
Kafka → notification-worker → уведомление → тестовый webhook
Redis → кеш каталога и rate limiter для API
```

Один репозиторий, один Go-модуль, несколько запускаемых процессов. Общая PostgreSQL допустима. Не нужны frontend, реальные платежи, Kubernetes, сложный RBAC и независимые микросервисы.

## Бизнес-правила

- Валюта одна; деньги — `int64` в минимальных единицах, не `float64`.
- Цена и сумма рассчитываются сервером; проверяются переполнение и допустимые границы.
- Количество товара положительное; повторяющиеся позиции товара в запросе отклоняются.
- Цена позиции сохраняется на момент создания заказа и затем не меняется.
- Остаток не может стать отрицательным.
- Резервирование заказа атомарно: все позиции либо ни одной.
- Статусы первой версии: `pending → confirmed` или `pending → rejected`.
- Терминальный статус не меняется при повторной обработке события.
- Пользователь видит только свои заказы.
- Один заказ не может повторно списать доступный остаток.
- Бизнес-данные хранятся в PostgreSQL; очистка Redis не уничтожает их.

## Контракты

### Данные

| Сущность | Обязательные данные |
|---|---|
| User | ID, имя, хеш API-ключа |
| Product | ID, уникальный SKU, название, цена, активность |
| Inventory | product_id, доступное количество |
| Order | ID, user_id, статус, сумма, причина отказа, timestamps |
| OrderItem | order_id, product_id, количество, цена покупки |
| Reservation | order_id, product_id, количество; уникальная пара заказ/товар |
| IdempotencyRecord | user_id, ключ, fingerprint запроса, order_id |
| OutboxEvent | event_id, тип, версия, payload, created_at, published_at |
| ProcessedEvent | имя обработчика, event_id; уникальная пара |
| Notification | ID, event_id, order_id, канал, статус, попытки, следующая попытка, последняя ошибка |

Добавляй поля при необходимости; объясняй ограничения и индексы в документации. API-ключи выдаются seed-командой; исходные ключи не хранятся в БД и не попадают в логи.

### HTTP

| Метод | Путь | Поведение |
|---|---|---|
| GET | `/products` | Каталог с ограниченной пагинацией |
| GET | `/products/{id}` | Карточка товара |
| POST | `/orders` | Создание pending-заказа, ответ 201 |
| GET | `/orders/{id}` | Заказ текущего пользователя |
| GET | `/orders` | Заказы текущего пользователя с пагинацией |
| GET | `/orders/{id}/notifications` | Уведомления по собственному заказу |
| GET | `/health/live` | Процесс работает |
| GET | `/health/ready` | Процесс готов выполнять свою функцию |

Для `POST /orders` обязателен `Idempotency-Key`. Область ключа — пользователь. Одинаковый ключ и эквивалентное нормализованное тело возвращают тот же заказ; другой payload — 409. Срок хранения ключей для первой версии не ограничен. Проверка и сохранение результата атомарны, включая конкурентные запросы.

Ошибки имеют единый JSON-формат: `code`, `message`, `request_id`. Предусмотреть 400, 401, 404, 409, 429, 500 и 503 по смыслу. Чужой заказ возвращает 404. Внутренние ошибки и SQL клиенту не выдаются.

### События

Topics: `orders.created.v1`, `orders.status-changed.v1`, `notifications.failed.v1`; отдельный DLQ для каждого consumer-потока. Ключ событий заказа — `order_id`.

```json
{
  "event_id": "uuid",
  "event_type": "order.created",
  "schema_version": 1,
  "occurred_at": "2026-10-24T10:00:00Z",
  "order_id": "uuid",
  "payload": {}
}
```

Контракт каждого payload документируется отдельно. Старые события должны оставаться читаемыми при добавлении необязательных полей; неизвестная несовместимая версия обрабатывается как ошибка контракта.

- [ ] Уникальность processed_event должна учитывать имя consumer-обработчика.
- [ ] Повторное событие не повторяет бизнес-эффект; повторное событие с новым event_id также защищается статусом заказа и бизнес-ограничениями.
- [ ] Добавить ограниченные retries с exponential backoff и jitter.

**Приёмка:** остановка Kafka не теряет созданный заказ; после восстановления outbox отправляется. Падение publisher после отправки приводит максимум к дублю. Падение consumer после commit БД до commit offset не повторяет резервирование.

**Отдельно решить:** если важен строгий порядок событий одного заказа, одного Kafka key недостаточно при переупорядочивании publisher. Для текущих однонаправленных переходов задокументировать границы; перед добавлением отмены определить версии событий и правила порядка.

## Обязательная матрица отказов

| Проверка | Ожидаемый итог |
|---|---|
| 100 заказов на остаток 10 | 10 подтверждений, 90 отказов, остаток 0 |
| Не хватает одного товара многопозиционного заказа | Ни одной резервации этого заказа |
| 20 параллельных запросов с одним Idempotency-Key | Один заказ |
| Тот же ключ с другим payload | 409, новый заказ не создан |
| Доставка одного события 5 раз | Один бизнес-эффект |
| Kafka остановлена во время создания заказа | Заказ и outbox сохранены, публикация догоняет после восстановления |
| Publisher убит после отправки, до отметки в БД | Дубль допустим, повторный бизнес-эффект отсутствует |
| Worker убит после commit БД, до commit offset | Повторная доставка безопасна |
| Redis остановлен или очищен | Заказы сохранны, fallback и limiter соответствуют документации |
| Невалидное событие | DLQ, дальнейшая обработка не блокируется навсегда |
| DLQ недоступен | Исходный offset не подтверждается преждевременно |
| Перезапуск во время retry уведомления | Счётчик и график попыток сохранены |
| Завершение процесса при активной работе | Ограниченное время остановки, работа завершена или безопасно повторится |

Для каждого эксперимента сохранить: подготовку, команду/действие сбоя, ожидаемый итог, фактические записи БД и результат. Не выдавать mock-тесты за проверку реальных интеграций.

## Итоговая самопроверка

Проект готов, когда ты можешь без подсказки объяснить:

1. Где заканчивается каждая транзакция и почему.
2. В каких местах возможны дубли и чем они обезвреживаются.
3. Что случится при падении процесса между любыми двумя шагами.
4. Кто владеет goroutines и как они завершаются.
5. Почему конкретный интерфейс нужен его потребителю.
6. Чем гарантии Kafka отличаются от гарантий всей системы.
7. Какие данные могут устареть в Redis и почему это допустимо.
8. Что показали нагрузка, race detector и профилирование.

Модули 0–5 — основа junior Go backend. Модули 6–10 — практика для развития к middle; важны самостоятельность, разбор компромиссов и реальные доказательства работы.
